# Укрепление ntpd-rs

Правильные системные часы критически важны как для безопасности, так и для надлежащей работы программного обеспечения. Например, определение действительности сертификата TLS зависит от системного времени. Запуск и отладка распределенной системы намного проще, а в некоторых случаях возможна только тогда, когда машины синхронизированы. Это руководство предоставляет некоторые рекомендации о том, о чем следует думать при укреплении ntpd-rs для вашей установки.

## Компромисс между доступностью и точностью

При укреплении ntpd-rs одной из больших проблем является фундаментальный компромисс между:

- доступностью синхронизации: ntpd-rs должен активно и постоянно синхронизироваться с внешними источниками
- риском неправильного управления: ntpd-rs не должен слепо следовать внешним источникам: они могут быть скомпрометированы

Многие меры против неправильного управления увеличивают риск недоступности и наоборот. Вы должны решить, какое правильное равновесие для вашего случая использования.

Например, риск неправильного управления велик, если ваша система работает с криптографией с открытым ключом. Безопасность текущей системы веб-сертификатов зависит от грубого (<1 день) согласия о том, какое сейчас время. Аналогично, безопасность и функционирование ваших приложений также могут быть затронуты. Компромисс, ограничивающий риск неправильного управления, вероятно, является правильным выбором.

С другой стороны, отсутствие синхронизации может вызвать проблемы в распределенной системе. Такие системы требуют малой верхней границы разницы во времени между машинами, на которых они работают. Когда синхронизация времени не удается, часы могут быстро отклониться за пределы этих границ и система может выйти из строя. Более того, может быть наиболее важным, чтобы машины были синхронизированы друг с другом, а не обязательно чтобы они использовали истинное время. Настройка ntpd-rs для максимальной доступности кажется лучшим подходом для этого сценария.

Поскольку универсального лучшего решения для этого компромисса не существует, вы как конечный пользователь должны рассмотреть, какой из этих факторов весит больше, и соответствующим образом настроить вашу конфигурацию.

## Ограничение неправильного управления

Ntpd-rs может запрашивать несколько удаленных серверов времени для получения текущего времени. Это позволяет ему обнаруживать и отбрасывать выбросы, которые предоставляют неправильное время. Алгоритм синхронизации всегда требует строгого большинства доступных серверов (тех, с которыми он может активно общаться), чтобы согласиться на текущее время перед внесением корректировок в часы. Более того, чтобы предотвратить атаку, при которой злоумышленник просто уменьшает доступные серверы только до своих собственных через атаки типа "отказ в обслуживании", минимальное количество согласующихся серверов также можно настроить через `minimum-agreeing-sources`.

В своей работе ntpd-rs влияет на часы двумя способами:

* **корректировка частоты:** ntdp-rs может регулировать частоту часов для компенсации аппаратных неточностей и медленной коррекции небольших смещений системных часов. Этот процесс может изменить часы в худшем случае не более чем на $1000$ микросекунд каждую секунду, что означает, что любое неправильное управление частотой потребует не менее 1000 дней, чтобы достичь смещения в 1 день.
* **корректировка шага** второй метод управления - это шаговое изменение часов. Это позволяет компенсировать большие ошибки, но также предоставляет больше возможностей злоумышленнику для введения больших ошибок в системные часы.

Корректировки частоты по существу невозможно использовать злоумышленнику. Угроза заключается в больших корректировках шага. Чтобы предотвратить неправильные корректировки шага, ntpd-rs позволяет настроить пределы шага. Когда эти пределы превышаются, демон предполагает, что произошла непоправимая проблема, и прекращает работу. Это означает, что синхронизация не произойдет и системное время будет отклоняться.

Пределы шага бывают трех вариантов:

- `single-step-panic-threshold` устанавливает пределы для любого отдельного шага во время операций. Использование этого может ограничить максимальное изменение часов, вызванное одной операцией.
- `startup-step-panic-threshold` применяется вместо `single-step-panic-threshold` во время первой коррекции часов после запуска. Его основное использование - позволить системам с плохими или отсутствующими часами реального времени все еще правильно синхронизировать свое время при запуске, даже когда установлен очень строгий `single-step-panic-threshold`.
- `accumulated-step-panic-threshold` ограничивает максимальную корректировку, выполненную через все корректировки часов, объединенные за время работы демона. Его можно использовать для обеспечения защиты от обхода порога паники шага через повторяющиеся шаги чуть ниже `single-step-panic-threshold`.

Какие значения выбрать для этих порогов, зависит от того, каким будет ожидаемое максимальное смещение системных часов во время нормальной работы и при запуске.

Снова обратите внимание, что пороги обеспечиваются через прекращение работы ntpd-rs при их превышении. Следовательно, строгие значения для них будут ограничивать способность демона автоматически корректироваться при внезапных изменениях часов, потенциально уменьшая доступность синхронизации времени.

При прекращении работы из-за вышеупомянутых порогов отображается сообщение в логе вроде приведенного ниже:
```
2024-11-28T12:40:32.821717Z  ERROR ntp_proto::algorithm::kalman: Unusually large clock step suggested, please manually verify system clock and reference clock state and restart if appropriate.
```

Если часы значительно неправильны, команду force-sync в [ntp-ctl](../man/ntp-ctl.8.md) можно использовать для ручной коррекции системных часов обратно к разумной начальной точке.

### Риски перезагрузки ntpd-rs

Поскольку `startup-step-panic-threshold` обычно выше, чем `single-step-panic-threshold`, перезагрузка ntpd-rs делает возможными более крупные корректировки шага. Более того, перезагрузка очищает общую накопленную корректировку, и повторные перезагрузки могут позволить злоумышленнику обойти защиты, предлагаемые `accumulated-step-panic-threshold`.

По этим причинам мы рекомендуем не перезапускать ntpd-rs автоматически. Скорее, администратор должен проверить остановленный процесс ntpd-rs, чтобы определить, безопасна ли перезагрузка в данный момент времени или может ли она усугубить текущую атаку. В последнем случае атака должна быть сначала устранена перед разрешением перезапуска демона ntpd-rs.

## Увеличение доступности

Лучший способ увеличить доступность синхронизации времени - увеличить количество серверов, которые ntpd-rs опрашивает для получения текущего времени. В сочетании с (относительно) небольшим значением для `minimum-agreeing-sources`, это позволит ntpd-rs продолжать синхронизировать локальное время, даже если несколько вышестоящих серверов выйдут из строя.

Для серверов, которые полностью недоступны, это разница между количеством настроенных источников времени и `minimum-agreeing-sources`. Однако обратите внимание, что не более половины серверов могут выйти из строя с неправильной информацией о времени, прежде чем это повлияет на синхронизацию времени.

Недостатком большого количества вышестоящих серверов времени является то, что злоумышленнику, нацеленному на неправильное управление вашими локальными часами, предоставляется больше возможностей для этого, потому что им нужно скомпрометировать меньшую часть вышестоящих серверов, чтобы получить контроль над часами. Затем злоумышленник может обеспечить синхронизацию с этим подмножеством через атаки типа "отказ в обслуживании" на другие вышестоящие серверы.

Если доступно недостаточно серверов для синхронизации времени или если они не согласны с текущим временем, это будет записано в лог в виде, аналогичном
```
2024-11-28T12:40:32.821717Z  INFO ntp_proto::algorithm::kalman: No consensus on current time
```
Обратите внимание, что это может происходить в определенные моменты, особенно при загрузке. Однако продолжительные периоды (более 15 минут) наблюдения этого сообщения, без каких-либо признаков синхронизации в виде строки лога, аналогичной
```
Sep 05 13:57:38 magnesium ntp-daemon[1593]: 2024-09-05T11:57:38.128571Z  INFO ntp_proto::algorithm::kalman: Offset: -84.4077443282968+-94.97527051033717ms, frequency: 0+-10000000ppm
```
означает, что клиент не управляет часами и может указывать на проблему с настроенными источниками времени.

## Конфигурация, логи и наблюдаемость

Есть и другие аспекты ntpd-rs, помимо управления часами, которые должны быть рассмотрены для безопасной работы.

Управление часами основано на файле конфигурации ntpd-rs. Если злоумышленник может изменить этот файл конфигурации, все настроенные в нем защиты теряют смысл. Мы рекомендуем использовать системные средства (например, разрешения) для ограничения того, кто может редактировать конфигурацию и, в зависимости от того, какие угрозы ожидаются, кто может читать ее.

Аналогично, для логов рекомендуется ограничить, кто может читать логи. Также настоятельно рекомендуется настроить ротацию логов и ограничения на максимальный размер лога через системные средства ведения логов, чтобы предотвратить случайное увеличение логов до размеров, препятствующих нормальной работе системы. При настройке с уровнем `log-level` info или выше, демон не должен регистрировать в ответ на случайный сетевой трафик. Однако объем вывода в лог пропорционален количеству настроенных удаленных источников времени.

Более того, демон ntpd-rs можно настроить на открытие двух сокетов:
- Сокет наблюдения доступен только для чтения и предоставляет некоторые источники и состояние
  алгоритма часов.
- Сокет конфигурации принимает команды и позволяет изменять некоторые
  параметры конфигурации.

Когда включены, эти сокеты по умолчанию открываются с довольно щедрыми
разрешениями (`0o666` для наблюдения и `0o660` для конфигурации). Для укрепленной установки может быть желательно дополнительно ограничить доступ к этим сокетам или оставить их отключенными. Конфигурация позволяет настроить более строгие разрешения для этих сокетов через параметры `observation-permissions` и `configure-permissions`.
