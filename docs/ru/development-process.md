# Процессы разработки

## Выпуск релизов

Новые релизы создаются путем старта либо от самого последнего коммита в main,
либо путем портирования исправлений поверх существующего тега. Некоторые вещи, на которые стоит обратить внимание
перед началом процесса выпуска:

- Все ли зависимости недавно обновлены с помощью `cargo update`?
- Содержит ли журнал изменений все недавние дополнения, удаления, изменения и исправления?
- Все ли еще открыты какие-либо проблемы в связанных с этим метках на GitHub?

Для определения версии, которую нужно выпустить, мы придерживаемся семантического версионирования:

- Если есть какие-либо (крупные) критические изменения, мы всегда выпускаем новую основную
  версию.
- Патч-версии, как правило, выпускаются только для небольших релизов, содержащих только исправления.
- Минорные версии выпускаются, когда вводятся большие исправления или новые функции.
- В любое время можно сделать новый dev-релиз, если неизвестно, какой будет следующий
  релиз, вы всегда должны предполагать изменение патч-версии и только
  увеличивать минорные или мажорные версии, если происходят какие-либо новые функции или критические изменения соответственно.
- Перед крупными релизами или если требуется тестирование, может быть
  выпущен бета-релиз или кандидат в релизы.

### Контрольный список

- [ ] Запустить `utils/update-version.sh [version]`
- [ ] Обновить `CHANGELOG.md` новой версией, удалить любой `Unreleased`
      раздел в журнале изменений. Убедиться, что версия для релиза - это самый верхний
      раздел журнала изменений. Также убедиться, что ссылка на diff обновлена в
      нижней части документа.
- [ ] `git switch -c release/[version]` (имя ветки должно соответствовать этому формату)
- [ ] `git commit -a -S -m "Release [version]"` (требуется подписанный коммит)
- [ ] `git push -u origin release/[version]`
- [ ] Дождаться завершения конвейеров github actions, обратить особое внимание на
      конвейер упаковки
- [ ] Перейти на страницу релизов на Github и найти черновик релиза, проверить, 
      правильно ли сгенерированы бинарные файлы.
- [ ] Попросить кого-нибудь просмотреть ветку
- [ ] ВНИМАНИЕ: объединять ветку с main только если она полностью актуальна по сравнению
      с main, не пропускать никакие другие ветки в очередь объединения в это время.
      Вы также можете сохранить релиз в не-main ветку, но в этом случае убедиться
      синхронизировать main ветку позже, чтобы обновить журнал изменений
      в main.
- [ ] Перейти на страницу релизов на GitHub и найти черновик релиза, отредактировать
      черновик релиза и сделать его публичным, это также должно создать тег в
      репозитории.
- [ ] На вашем локальном компьютере, переключиться на конкретный коммит, который был помечен
      GitHub (т.е. `git fetch && git switch --detach v[version]`)
- [ ] Запустить `utils/release.sh` для публикации пакетов на crates.io
