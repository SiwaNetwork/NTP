# Переход с ntpd

И [ntpd](https://www.ntp.org/), эталонная реализация NTP, и ntpd-rs могут выполнять схожую роль в системах Unix. Это руководство по преобразованию конфигурации ntpd в конфигурацию ntpd-rs. Мы предполагаем наличие некоторого опыта работы с [форматом конфигурации ntpd](https://www.ntp.org/documentation/4.2.8-series/comdex/). Пользователю без опыта работы с ntpd или с небольшим опытом может быть лучше следовать нашему [руководству по началу работы](getting-started.md).

Конфигурация для ntpd использует пользовательский формат, который работает как список команд. В отличие от этого, ntpd-rs использует файл конфигурации в формате `.toml`, который присваивает значения свойствам. Это означает, что в большинстве случаев поля не могут повторяться. Комментарии можно добавлять, начиная их с `#`. Остальная часть строки затем игнорируется.

Конфигурация `ntpd-rs` может быть проверена с помощью `ntp-ctl validate -c <path>`. Это проверит все имена полей, и в некоторых случаях проверит, что значение находится в пределах диапазона допустимых значений для этого свойства.

Это руководство не будет рассматривать все директивы конфигурации ntpd, а скорее сосредоточится на тех, которые наиболее важны для успешной миграции. Если конкретная директива здесь не упомянута, в [справочнике по конфигурации](../man/ntp.toml.5.md) все еще могут быть параметры ntpd-rs, которые достигают желаемого эффекта. Обратите внимание, что в настоящее время не вся функциональность ntpd поддерживается, краткий обзор основных различий приведен [в конце этого документа](#unsupported-features).

## Источники времени

Команды `server` и `pool` имеют прямой эквивалент в ntpd-rs:

```toml
# ntpd
server 0.pool.ntp.org
server 1.pool.ntp.org
pool pool.ntp.org

# ntpd-rs
[[source]]
mode = "server"
address = "0.pool.ntp.org"

[[source]]
mode = "server"
address = "1.pool.ntp.org"

[[source]]
mode = "pool"
address = "pool.ntp.org"
count = 4
```

Источник в режиме `pool` должен явно определять целое число `count`, максимальное количество соединений из этого пула. Демон ntpd-rs будет активно пытаться поддерживать "заполнение" пула: новые соединения будут запускаться, если источник из пула недоступен.

Симметричные и широковещательные режимы ассоциаций намеренно не поддерживаются в ntpd-rs, потому что эти режимы имеют проблемы с безопасностью. Команда `peer` может быть заменена стандартным источником `server`. Для команды `broadcast` альтернативой может быть настройка NTP-сервера через DHCP

Прямого эквивалента флагов `maxpoll` и `minpoll` ntpd, которые можно настроить для каждого источника, нет. Вместо этого ntpd-rs определяет границы интервала опроса глобально для всех источников времени:
```toml
[source-defaults]
poll-interval-limits = { min = <minpoll>, max = <maxpoll> }
initial-poll-interval = <желаемый начальный интервал опроса>
```

В ntpd-rs пока нет поддержки всплесков, но алгоритм ntpd-rs способен синхронизироваться намного быстрее (с меньшим количеством измерений), чем алгоритм ntpd. Поэтому, если присутствует какая-либо директива всплеска (`burst` или `iburst`), их обычно можно игнорировать при переводе конфигураций. В некоторых случаях, если установлены строгие пользовательские ограничения опроса, их может потребоваться ослабить.

### Эталонные часы

Текущая версия ntpd-rs еще не поддерживает локальные эталонные часы, но эта функция есть в нашем плане работ. Если вы заинтересованы в миграции конфигурации с использованием локальных эталонных часов, мы были бы заинтересованы в услышании деталей. Эта информация поможет направить наши усилия по реализации.

## Параметры синхронизации времени

Минимальное количество источников времени, необходимое для синхронизации времени в ntpd-rs, настраивается через `minimum-agreeing-sources`:
```toml
[synchronization]
minimum-agreeing-sources = <minsources>
```
Если доступно меньше согласующихся источников, синхронизация не выполняется и часы будут отклоняться. Эта опция является комбинацией `minclock` и `minsane` в ntpd. Ее значение по умолчанию - 3, рекомендуемое значение с точки зрения безопасности. В ntpd используется значение по умолчанию 3 для `minclock` и 1 для `minsane`.

Через флаги `step` и `stepout` команды `tinker` ntpd позволяет ограничить максимальное изменение времени. Хотя функционально не совсем то же самое, ntpd-rs позволяет применять аналогичные ограничения через несколько порогов паники. Шаги при запуске контролируются через `startup-panic-threshold`, в то время как шаги во время нормальной работы контролируются с помощью `single-step-panic-threshold` и `accumulated-step-panic-threshold`.
```toml
[synchronization]
single-step-panic-threshold = 1000
startup-step-panic-threshold = { forward="inf", backward = 86400 }
accumulated-step-panic-threshold = "inf"
```

ntpd и ntpd-rs используют разные алгоритмы для синхронизации времени. Это означает, что параметры настройки фильтрации времени значительно различаются, и мы не можем предложить точное руководство по переводу параметров ntpd в значения для ntpd-rs. При миграции конфигурации, которая настраивает алгоритм ntpd, нужно принять во внимание намерение настройки и использовать это как руководство при выборе [параметров синхронизации времени](../man/ntp.toml.5.md#synchronization) ntpd-rs для изменения.

## Конфигурация сервера и контроль доступа

[Команда `restrict`](https://www.ntp.org/documentation/4.2.8-series/accopt/) используется в ntpd для отказа в запросах от клиента. В ntpd это глобальная настройка. Флаг настраивает, что происходит с соединениями от этого клиента. Например, `ignore` будет молча игнорировать запрос, а `kod` отправит ответ клиенту, уведомляющий его о том, что его запрос отклонен.

Эта логика выражена по-другому в ntpd-rs. Конкретный сервер может быть настроен с `denylist` и `allowlist`.
Подсети для разрешения или запрета должны быть указаны в нотации CIDR
(IP-адрес, за которым следует косая черта и количество замаскированных битов, например `127.0.0.1/8` или `192.168.1.1/24`)

```toml
[[server]]
listen="<ip или [::]>:<port>"

[server.allowlist]
filter = [
    "<subnet1>",
    "<subnet2>",
]
action = "ignore"

[server.denylist]
filter = [
    "<subnet3>",
    "<subnet4>",
]
action = "deny"
```

Конфигурации списков разрешений и запретов обе необязательны в ntpd-rs. По умолчанию, если сервер настроен, он будет принимать трафик откуда угодно. При настройке обоих списков разрешений и запретов ntpd-rs сначала проверит, находится ли удаленный адрес в списке запретов. Только если это не так, будет рассмотрен список разрешений.

Свойства `allowlist.action` и `denylist.action` могут иметь два значения:

- `ignore` соответствует `ignore` в ntpd и молча игнорирует запрос
- `deny` соответствует `kod` в ntpd и отправляет пакет отказа kiss-o'-death

Стратум можно настроить в ntpd-rs с помощью ключа `local-stratum`:
```toml
[synchronization]
local-stratum = <stratum>
```

## Неподдерживаемые функции

Не вся функциональность в ntpd в настоящее время имеет эквивалент в ntpd-rs. В частности, следующие основные функции в настоящее время не имеют хороших альтернатив в ntpd-rs:

- Локальные аппаратные устройства в качестве источников времени.
- Поддержка аутентификации NTP MAC.
- Отметка подмножеств источников как более доверенных, чем другие
- Режимы протокола, кроме сервера и клиента
- Всплески
Если какие-либо из этих функций критичны для вашего случая использования, ntpd-rs может быть пока не вариантом для вас. Пожалуйста, сообщите нам, если вам не хватает этих функций или вы хотите спонсировать какие-либо из них, так как это помогает нам определять приоритеты нашей работы.
