# Переход с chrony

И chrony, и ntpd-rs могут выполнять схожую роль в системах Unix. Это руководство направлено на помощь тем, кто мигрирует машины, в настоящее время работающие под управлением chrony, на ntpd-rs. Мы предполагаем наличие некоторого опыта работы с [форматом конфигурации chrony](https://chrony-project.org/doc/4.3/chrony.conf.html). Пользователю без опыта работы с chrony или с небольшим опытом может быть лучше следовать нашему [руководству по началу работы](getting-started.md).

Прежде чем мы начнем с особенностей преобразования отдельных директив, сначала несколько замечаний. В отличие от формата конфигурации chrony, который действует как список команд для клиента, конфигурация ntpd-rs представляет собой файл [TOML](https://toml.io/). В частности, это означает, что конфигурация выполняется путем присвоения значений свойствам. Таким образом, поля не могут повторяться, если только они не являются частью списка, например, с разделами `[[source]]` и `[[server]]`. Комментарии можно добавлять, начиная их с `#`. Остальная часть строки затем игнорируется.

Обратите внимание, что для некоторых из приведенных ниже настроек ntpd-rs и chrony используют разные значения по умолчанию. При преобразовании конфигурации обращайте особое внимание на `minsources`/`minimum-agreeing-sources`, `maxstep` и соответствующие `-panic-thresholds`, а также любые настройки функциональности сервера NTS. Проверку результирующей конфигурации ntpd-rs можно выполнить с помощью `ntp-ctl validate -c <path>`, которая должна хотя бы отловить самые грубые ошибки.

Это руководство не рассматривает все директивы конфигурации chrony, а скорее сосредоточено на тех, которые наиболее важны для успешной миграции. Если директива здесь не упомянута, в [справочнике по конфигурации](../man/ntp.toml.5.md) все еще могут быть параметры ntpd-rs, которые достигают желаемого эффекта. Обратите внимание, что в настоящее время не вся функциональность chrony поддерживается, краткий обзор основных различий приведен [в конце этого документа](#non-supported-features)

## Источники времени

### Директивы сервера

Соединения клиент-сервер нужно мигрировать одним из двух способов:
- Как источник сервера, если не используется аутентификация.
- Как источник NTS, если NTS включен (т.е. опция NTS присутствует в директиве сервера).

Для директив сервера без аутентификации их можно преобразовать в
```toml
[[source]]
mode="server"
address="<address>"
```
где адрес такой же, как тот, что указан в директиве сервера.

Для директив сервера с NTS их можно преобразовать в
```toml
[[source]]
mode="nts"
address="<address>"
```

Если директива сервера содержит ограничения опроса (`maxpoll` или `minpoll`), их нельзя указать для каждого сервера в ntpd-rs. Лучший подход - определить значения, приемлемые для всех источников времени, и применить их через настройки источника по умолчанию:
```toml
[source-defaults]
poll-interval-limits = { min = <minpoll>, max = <maxpoll> }
initial-poll-interval = <желаемый начальный интервал опроса>
```

В ntpd-rs пока нет поддержки всплесков. Когда присутствует любая директива всплеска (`burst` или `iburst`), их обычно можно игнорировать, хотя если установлены пользовательские ограничения опроса, их может потребоваться пересмотреть.

Для NTS, если набор пользовательских сертификатов настроен для источника через директиву `certset`, их можно предоставить через параметр ntpd-rs `certificate_authority`. Это ожидает путь к файлу, содержащему все принятые корневые сертификаты для источника, принятые в дополнение к системным сертификатам.

### Директивы пула

Пулы, настроенные через директиву пула, можно добавить в конфигурацию ntpd-rs через
```toml
[[pool]]
mode="pool"
address="<address>"
```

Если директива пула указывает `maxsources`, это значение можно настроить в ntpd-rs через свойство `count`. Значение по умолчанию (4) такое же между ntpd-rs и chrony.

Если директива пула содержит ограничения опроса (`maxpoll` или `minpoll`), их нельзя указать для каждого сервера в ntpd-rs. Лучший подход - определить значения, приемлемые для всех источников времени, и применить их через настройки источника по умолчанию:
```toml
[source-defaults]
poll-interval-limits = { min = <minpoll>, max = <maxpoll> }
initial-poll-interval = <желаемый начальный интервал опроса>
```

В настоящее время в ntpd-rs нет поддержки всплесков. Когда присутствует любая опция всплеска (`burst` или `iburst`), их обычно можно игнорировать, хотя если установлены пользовательские ограничения опроса, их может потребоваться ослабить.

### Директивы источника времени

Симметричные режимы пиров не поддерживаются в ntpd-rs и вряд ли будут поддерживаться в будущем. При миграции конфигурации с симметричными соединениями пиров мы рекомендуем заменить их соединениями в режиме клиент-сервер на обоих клиентах (см. также [Директивы сервера](#server-directives) выше).

### Директивы Refclock

Текущая версия ntpd-rs еще не поддерживает локальные эталонные часы, но эта функция есть в нашем плане работ. Если вы заинтересованы в миграции конфигурации с использованием локальных эталонных часов, мы были бы заинтересованы в услышании деталей. Эта информация может помочь направить наши усилия по реализации.

## Параметры синхронизации времени

Минимальное количество источников, необходимое для синхронизации времени в ntpd-rs, настраивается через `minimum-agreeing-sources`:
```toml
[synchronization]
minimum-agreeing-sources = <minsources>
```
Обратите внимание, что хотя эффект этой опции такой же, как у `minsources` в chrony, значение по умолчанию в ntpd-rs - 3, а не 1 источник, требуемый по умолчанию chrony. Хотя 3 рекомендуется для безопасности, это может быть неуместно для всех конфигураций, особенно для конфигураций, где настроено мало удаленных источников.

Chrony может ограничить максимальное изменение времени директивой `maxchange`. ntpd-rs позволяет применять аналогичные ограничения через несколько порогов паники. Шаги при запуске контролируются через `startup-panic-threshold`, в то время как шаги во время нормальной работы контролируются с помощью `single-step-panic-threshold` и `accumulated-step-panic-threshold`. В отличие от chrony, они не позволяют игнорировать первые несколько случаев, и что более важно, имеют конечные значения по умолчанию:
```toml
[synchronization]
single-step-panic-threshold = 1000
startup-step-panic-threshold = { forward="inf", backward = 86400 }
accumulated-step-panic-threshold = "inf"
```

Chrony и ntpd-rs используют разные алгоритмы для синхронизации времени. Это означает, что параметры настройки фильтрации времени значительно различаются, и мы не можем предложить точное руководство по переводу параметров chrony в значения для ntpd-rs. При миграции конфигурации, которая настраивает алгоритм chrony, нужно принять во внимание намерение настройки и использовать это как руководство при выборе [параметров синхронизации времени](../man/ntp.toml.5.md#synchronization) для изменения.

При настройке алгоритма синхронизации важно отметить крупное философское различие между chrony и ntpd-rs. Для chrony большинство параметров настройки алгоритма устанавливаются для отдельного источника времени. Внутри ntpd-rs весь контроль фильтрации осуществляется через глобальные параметры. Хотя мы не ожидаем, что это будет так, если у вас есть конкретные параметры, которые вы хотели бы настроить для каждого источника, пожалуйста, сообщите нам об этом, чтобы мы могли рассмотреть это для будущих выпусков.

## Конфигурация сервера

Конфигурация сервера в ntpd-rs работает немного иначе, чем в chrony. Вместо включения функции сервера времени путем разрешения удаленных соединений с сервером, можно настроить один или несколько экземпляров обслуживания. Каждый из них поставляется со своим собственным списком разрешений и запретов.
Подсети для разрешения или запрета должны быть указаны в нотации CIDR
(IP-адрес, за которым следует косая черта и количество замаскированных битов, например `127.0.0.1/8` или `192.168.1.1/24`)

```toml
[[server]]
listen="<ip или [::]>:<port>"

[server.allowlist]
filter = [
    "<subnet1>",
    "<subnet2>",
]
action = "ignore"

[server.denylist]
filter = [
    "<subnet3>",
    "<subnet4>",
]
action = "deny"
```

Конфигурации списков разрешений и запретов обе необязательны в ntpd-rs. По умолчанию сервер принимает трафик откуда угодно. При настройке обоих списков разрешений и запретов ntpd-rs сначала проверит, находится ли удаленный адрес в списке запретов. Только если это не так, будет рассмотрен список разрешений. Это упорядочивание нужно учитывать при переводе переплетенных комбинаций команд `allow` и `deny` chrony.

NTS можно включить для сервера, настроив сервер обмена ключами NTS:
```toml
[[nts-ke-server]]
listen = "<IP или [::]>:4460"
certificate-chain-path = <ntsservercert>
private-key-path = <ntsserverkey>
```
Здесь используются имена соответствующих директив chrony с правой стороны присваивания. Обратите внимание, что в отличие от chrony, ntpd-rs не имеет IP-адреса по умолчанию, на котором он прослушивает трафик NTS-KE: его нужно предоставить явно. Порт, однако, является необязательным и по умолчанию принимает стандартное значение 4460.

Ключи, используемые для шифрования куки, по умолчанию являются эфемерными. Если их нужно сохранять при перезагрузках сервера, путь для хранения можно настроить:
```toml
[keyset]
key-storage-path = <путь к хранилищу ключей>
```
Обратите внимание, что в отличие от директивы `ntsdumpdir` chrony, здесь нужно указать полный путь, и нет пути по умолчанию.

Интервал ротации ключей по умолчанию - ежедневно, и сохраняется на одну полную неделю старых ключей для обслуживания клиентов со старыми куки.
С этими настройками куки для сервера действительны только немного более чем одну неделю. Это намного меньше, чем значение по умолчанию в chrony - 3 недели.
Эти настройки можно изменить с помощью параметров `key-rotation-interval` и `stale-key-count`:
```toml
[keyset]
stale-key-count = <количество старых ключей для хранения>
key-rotation-interval = <интервал ротации в секундах>
```

Обмен ключами, с помощью которых шифруются куки NTS, между несколькими серверами ntpd-rs пока не поддерживается.

Если локальный стратум для сервера настроен через `local stratum`, его можно настроить в ntpd-rs через ключ `local-stratum`:
```toml
[synchronization]
local-stratum = <stratum>
```

Режим вещания не поддерживается в ntpd-rs. Если это используется в вашей текущей настройке, альтернативой может быть настройка NTP-сервера через DHCP. Обратите внимание, что использование режима вещания может оставить вас более уязвимым к проблемам безопасности.

## Неподдерживаемые функции

Не вся функциональность в chrony в настоящее время имеет эквивалент в ntpd-rs. В частности, следующие основные функции в настоящее время не имеют хороших альтернатив в ntpd-rs:

- Локальные аппаратные устройства в качестве источников времени.
- Поддержка аутентификации NTP MAC.
- Отметка подмножеств источников как более доверенных, чем другие.
- Выступление в качестве источника данных о високосных секундах.

Если какие-либо из этих функций критичны для вашего случая использования, ntpd-rs может быть пока не вариантом для вас. Пожалуйста, сообщите нам, если вам не хватает этих функций или вы хотите спонсировать какие-либо из них, так как это помогает нам определять приоритеты нашей работы.
