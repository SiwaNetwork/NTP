# Сетевая защита времени

Сетевая защита времени (NTS) - это расширение протокола NTP, направленное на
обеспечение безопасности связи между NTP-клиентами и серверами. Его самые важные
цели:

* Проверка идентичности сервера, чтобы убедиться, что вы получаете время от
  источника, от которого вы ожидали получить информацию о времени.
* Убедиться, что пакеты времени подлинные, т.е. они не были изменены в
  пути передачи.
* Предотвращение воспроизведения ранее отправленных пакетов времени и проверка того, что
  пакеты времени были отправлены в ответ на запрос клиента.

Хотя NTS имеет возможность шифровать части сообщения, информация о времени
сама по себе считается общедоступной информацией и, как таковая, не
шифруется. Третьи лица могут видеть, какой была обмененная информация о времени,
но они не могут изменить её.

## Использование источника NTS
Вы можете использовать существующие публичные серверы NTS с ntpd-rs, просто добавив источник
с режимом `nts`. Например, [netnod] имеет публичные серверы NTS, для использования которых вы
просто настраиваете источник следующим образом:

[netnod]: https://www.netnod.se/nts/network-time-security

```toml
[[source]]
mode = "nts"
address = "nts.netnod.se"
```

Сертификат сервера NTS проверяется с использованием установленных системных
сертификатов на вашей машине. Однако некоторые серверы NTS используют пользовательский или частный
центр сертификации (CA), который неизвестен вашей системе для подписи своих
сертификатов, в таких случаях вам также нужно будет указать дополнительный
центр сертификации, установив параметр `certificate-authority`:

```toml
[[source]]
mode = "nts"
address = "my.private.server.example.com"
certificate-authority = "/path/to/certificate/authority.pem"
```

!!! Warning

    Демон ntpd-rs не поддерживает самоподписанные сертификаты. Серверы, которые
    имеют только самоподписанный сертификат, не могут быть использованы. Либо настройте частный
    центр сертификации и используйте этот CA для подписания сертификата для
    сервера, либо выберите альтернативный сервер NTS.

## Протокол NTS
При использовании NTS и клиент, и сервер подписывают и частично шифруют NTP
сообщения, которыми они обмениваются, с использованием симметричной криптографии. Для этого клиент
и сервер сначала должны обменяться ключами, которые будут использовать. NTS решает эту
проблему с отдельным обменом ключами.

Для обмена ключами клиент сначала связывается с сервером по TCP-соединению
с защищенным TLS, тем же протоколом, который используется для безопасного веб-просмотра. По этому
соединению они затем решают, какие ключи использовать. Наконец, сервер предоставляет
клиенту восемь куки. Эти куки используются клиентом, чтобы сообщить серверу,
какие ключи используются для сеанса. Клиент использует каждую куки только
один раз, чтобы обеспечить невозможность отслеживания его соединения третьими лицами, и он получает новую куки с каждым ответом сервера.

Эти куки являются непрозрачным мешком байтов для клиента, и сервер может поместить
в них всё, что он находит полезным для идентификации соответствующих ключей для этого
конкретного клиента. Однако куки должны быть уникальными, куки не могут быть
повторно использованы после отправки сообщения с ними. Если клиент когда-либо исчерпывает куки
(куки теряется всякий раз, когда сообщение NTP или ответ на него теряется)
или если сервер каким-то образом больше не понимает куки, которые он получает
от клиентов, сервер и клиент должны повторить обмен ключами.

## Настройка сервера NTS
Настройка сервера NTS включает в себя несколько шагов. Прежде чем начать, убедитесь
что у вас уже есть [работающий NTP-сервер](./server-setup.md).

Для части обмена ключами в NTS нам нужно настроить определенный сервер обмена
ключами в демоне. Серверы NTS-KE по умолчанию работают на TCP-порту 4460. Обратите внимание
на разницу здесь, где NTP-сервер использует UDP по сравнению с протоколом обмена ключами,
работающим по TCP. Для этого мы добавляем раздел `[[nts-ke-server]]` в нашу
конфигурацию:

```toml
[[nts-ke-server]]
listen = "[::]:4460"
certificate-chain-path = "/path/to/certificate/chain.pem"
private-key-path = "/path/to/private.key"
```

!!! Note

    Демон ntpd-rs в настоящее время не поддерживает работу NTS-сервера без
    связанного доменного имени, через которое клиенты получают к нему доступ. Если вы
    настраиваете свой собственный частный CA, вы можете, тем не менее, настроить локальное доменное имя
    (например, `example-nts.local`), например, настроенное через `/etc/hosts`.
    Сырые IPv4 или IPv6 адреса, такие как `192.168.1.1`, не поддерживаются.

После настройки сервера NTS-KE NTP-сервер, который вы настроили в своем
конфигурации, автоматически начнет отвечать на действительные сообщения NTS, нет
дополнительной настройки, необходимой.

Получение сертификата для вашего сервера может быть довольно сложным процессом. Мы
рекомендуем использовать клиент [Let's Encrypt][1] ACME для настройки TLS
сертификата (аналогично тому, как вы бы настроили это для веб-сервера). Ниже вы
найдете несколько примеров с использованием популярных клиентов.

[1]: https://letsencrypt.org/

!!! Note

    Для целей разработки (или в очень специфических сетевых сценариях) может
    быть полезно настроить свой собственный CA, который позволяет настроить частный
    сертификат для вашего NTS-сервера. Это не рекомендуется для общего использования,
    но у нас есть руководство по [настройке своего собственного CA](../development/ca.md).

### Настройка хранения ключей
После включения сервера NTS-KE у вас будет рабочая конфигурация для
NTS-сервера. Однако каждый раз, когда мы перезагружаем наш сервер, все его клиенты будут
должны снова пройти процесс обмена ключами. Чтобы убедиться, что клиенты не
испытывают никаких негативных последствий при перезагрузке сервера, мы можем настроить
сервер для хранения материалов ключей, которые он генерирует, на диске. Мы можем сделать это, добавив
дополнительный раздел `[keyset]` и установив `key-storage-path` в нем:

```toml
[keyset]
key-storage-path="/path/to/store/key/material"
```

Обратите внимание, что, как и с закрытым ключом TLS, злоумышленник, имеющий доступ к файлу
указанному под `key-storage-path`, может скомпрометировать все соединения с клиентами.
Кроме того, демон не будет создавать какие-либо родительские каталоги, если их не существует.
Он создаст файл, если его не существует.

### Сертификаты с использованием certbot
Let's encrypt рекомендует использовать certbot для управления сертификатами на вашем сервере.
Чтобы начать, вы должны следовать [инструкциям по установке certbot][2].
Вы можете следовать инструкциям для *'Другое'* программное обеспечение для вашей конкретной ОС.
После установки certbot проверьте, что он работает должным образом:

[2]: https://certbot.eff.org/instructions

```sh
certbot --version
```

После установки certbot вы можете выполнить простую команду для получения сертификата
для вашего домена, заменив адрес электронной почты и доменное имя своими:

```sh
certbot certonly --standalone -n --email "[you@example.com]" --agree-tos -d "[time.example.com]" --deploy-hook "systemctl restart ntpd-rs"
```

Команда выше предполагает, что трафик с TCP-порта 80 может быть получен из
интернета вашим сервером и что нет другого программного обеспечения (например, другого
веб-сервера), работающего на этом порту. Когда у вас уже есть существующий веб-сервер,
слушающий порт 80, вы можете использовать его тоже. Или если http-трафик невозможен,
вы также можете использовать проверку на основе DNS, но это выходит за рамки этого
руководства. Пожалуйста, прочитайте [документацию certbot][3] для получения более подробной информации.

Certbot автоматически настраивает задачу, которая обновляет эти сертификаты, потому что
сертификаты Let's Encrypt действительны только 90 дней. Аргумент `--deploy-hook`
говорит certbot перезапустить демон ntpd-rs всякий раз, когда выдается
новый сертификат, потому что ntpd-rs не перезагружает файлы сертификатов автоматически.

Теперь мы можем обновить нашу конфигурацию с путями сгенерированных файлов
сертификатов (заменяя доменное имя доменным именем, для которого вы запросили
сертификат):

```toml
[[nts-ke-server]]
listen = "[::]:4460"
certificate-chain-path = "/etc/letsencrypt/live/[time.example.com]/fullchain.pem"
private-key-path = "/etc/letsencrypt/live/[time.example.com]/privkey.pem"
```

Наконец, перезапустите демон ntpd-rs с помощью `systemctl restart ntpd-rs`. Ваш
сервер теперь должен быть способен обрабатывать NTS-трафик!

[3]: https://eff-certbot.readthedocs.io/en/stable/using.html

### Сертификаты с использованием lego
Lego - это альтернативная реализация клиента Let's Encrypt. Во многих ОС она может
быть установлена из репозитория пакетов путем поиска пакета `lego`. Если
она недоступна от вашего поставщика ОС, вы также можете найти загрузку со
[страницы lego github][4].

Для генерации нового сертификата вы можете выполнить следующую команду, заменив
адрес электронной почты и доменное имя своими:

```sh
lego --email "[you@example.com]" --http --domains "[time.example.com]" --accept-tos --path /var/lib/lego run
```

Lego не обновляет сертификаты автоматически при их истечении, но мы можем
настроить запись в crontab для автоматизации процесса обновления. Команда lego renew
обновляет только тогда, когда сертификату необходимо истечь. Для этого поместите исполняемый
сценарий оболочки в `/etc/cron.daily` (заменяя адрес электронной почты и доменное имя
своими, как и раньше):

```sh
cat <<'EOF' > /etc/cron.daily/renew-certificate
#!/usr/bin/env bash
lego --email "[you@example.com]" --http --domains "[time.example.com]" --accept-tos --path /var/lib/lego renew --renew-hook "systemctl restart ntpd-rs
EOF
chmod +x /etc/cron.daily/renew-certificate
```

Поскольку демон ntpd-rs не перезапускается автоматически всякий раз, когда
сертификаты обновляются, мы указываем lego перезапустить наш демон с помощью
аргумента `--renew-hook`.

Команды выше предполагают, что трафик с TCP-порта 80 может быть получен из
интернета вашим сервером и что нет другого программного обеспечения (например, другого
веб-сервера), работающего на этом порту. Когда у вас уже есть существующий веб-сервер,
слушающий порт 80, вы можете использовать его тоже. Или если http-трафик невозможен,
вы также можете использовать проверку на основе DNS, но это выходит за рамки этого
руководства. Пожалуйста, прочитайте [документацию lego][5] для получения более подробной информации.

Теперь мы можем обновить нашу конфигурацию с путями сгенерированных файлов
сертификатов (заменяя доменное имя доменным именем, для которого вы запросили
сертификат):

```toml
[[nts-ke-server]]
listen = "[::]:4460"
certificate-chain-path = "/var/lib/lego/certificates/[time.example.com].crt"
private-key-path = "/var/lib/lego/certificates/[time.example.com].key"
```

Наконец, перезапустите демон ntpd-rs с помощью `systemctl restart ntpd-rs`. Ваш
сервер теперь должен быть способен обрабатывать NTS-трафик!

[5]: https://go-acme.github.io/lego/
